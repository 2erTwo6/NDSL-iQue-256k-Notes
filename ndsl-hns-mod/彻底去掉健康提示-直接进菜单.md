# 彻底去掉开机健康提示、直接进菜单 —— 改法与取舍

本文件说明**如何让开机"健康与安全提示"页面完全不出现、直接进 DS 菜单**，
以及每种改法的代价、所需的 `0x06` 校验值、以及**是否需要重新压缩 Part1**。

> 与 `README.md` 的分工：README 讲的是**自动跳过**（警告页照原版绘制、只是不用点，
> 即 `hns-autoskip`）；本文件讲的是**页面根本不出现**的几种改法。
>
> ⚠️ 真机刷写必读：本目录上层项目已经证明过"**模拟器通过 ≠ 真机通过**"
> （`dsfwtool -comp` 压出的流软件校验全过、melonDS 正常，真机纯白屏）。
> 因此下面每条改法都标注了**是否需要重新压缩 Part1**——不需要重压的改法，
> 对真机是**零编码器风险**，优先级最高。

工作基准（本次所有数据都在这份原厂固件上实测得出）：

```
../我的固件/FW001656B0043F/firmware.bin   md5 86f3adf73fe072593772cefb6f6426e9
../我的固件/FW001656B0043F/biosnds7.rom  md5 df692a80a5b1bc90728bc3dfc76cd948
5 项校验全部复现：0x06=0x0F1F 0x04=0xDB00 0x26=0x4F5D 0x2A=0xB3E6 设置=0x3889
```

## 0. 结论速查表

| # | 改法 | Part1 解压后改动 | 新 `0x06` | 警告页是否显示 | 是否需重压 Part1 | 真机风险 |
|---|---|---|---|---|---|---|
| **A** | `hns-autoskip`（当前成品） | `0x0A0C: 23 48→1A E0` | `0xCFC3` | **会显示**（原版淡入，1.5s 后自动走） | ❌ 不需要 | 最低 |
| **B** | 只跳阶段（最小改动） | `0x1352: 00 21→02 21` | `0xBF2F` | **不显示** | ❌ 不需要 | 最低 |
| **C** | 跳阶段 + 关掉等待（推荐"彻底"） | `0x1352: 00 21→02 21`<br>`0x0A0C: 23 48→1A E0` | `0x7FF3` | **不显示** | ❌ 不需要 | 最低 |
| **D** | = 当年那版 "v4"：跳阶段 + 瞬时淡出 + **不装载** | `0x133C: 04 F0 A6 F9→C0 46 C0 46`<br>`0x1352: 00 21→02 21`<br>`0x089A: 0F 29→00 29` | `0xDB32` | **不显示、不装载、无过渡动画** | ✅ 需要 | 较高（编码器必须被真机接受） |
| **E** | 不装载 + 跳阶段（保留 stage2 淡出） | `0x133C: 04 F0 A6 F9→C0 46 C0 46`<br>`0x1352: 00 21→02 21` | `0x248A` | **不显示、不装载**，还剩一段淡出 | ✅ 需要 | 较高 |

- **要"页面完全不出现"且对真机最安全 → 选 C**（全部落在字面量上，可以不重压）。
- **要"连画面数据都不装载 + 完全没有过渡动画" → 选 D**（就是你说"很完美但太野"的那版）。
- A 不是"彻底"：它只是自动跳过，警告页仍会按原版画出来。

## 1. 先说清楚："彻底"有两种含义

| 含义 | 能否做到 | 需要改什么 |
|---|---|---|
| ① 警告页面**不显示**（开机看不到它） | ✅ 可以 | 让 stage 链跳过 stage0（淡入）/stage1（等待）：`0x1352: stage=2` |
| ② 警告画面数据**根本不装载/绘制** | ✅ 可以，但需重压 | 再把 `0x133C: bl 0x568C`（装载该语言警告画面）nop 掉 |
| ③ **连过渡动画都没有**（画面"啪"地出现） | ✅ 可以，但需重压 | 再把 `0x089A` 的 15 帧淡出改成瞬时 |

B/C 做到 ①；D 做到 ①+②+③。**没有任何改法能让"零帧黑屏/logo"**：BIOS 自身 logo、
固件显示初始化与 GUI（P3/P5）解压载入是固定开销，原版就是拿警告页盖住这段时间的。

## 2. 为什么 B / C 能做到"零重压风险"（本次实测证据）

`0x0A0C`、`0x1352` 这些字节在任天堂的 LZ77 压缩流里**恰好都是"字面量"**，
不是被匹配回引的字节。把补丁施加到解压后镜像再重新压缩，**流里只有那几个字节变化**：

| 改法 | 压缩流长度 | **压缩流内差异字节数** | 差异位置 |
|---|---|---|---|
| A | 51223（原版 51223） | **2** | `+0x886`、`+0x888`（正是被改的两个字面量） |
| B | 51223 | **1** | `+0x105D` |
| C | 51223 | **3** | `+0x886`、`+0x888`、`+0x105D` |
| D | 51227（+4，槽位 51232 仍放得下） | 47638 | 含匹配内字节 → 整条流重排 |
| E | 51225 | 45597 | 同上 |

**含义**：A/B/C 的"重新压缩"结果 = "把原版流里对应字面量原地改掉"，
两者**逐字节等价**。所以这三种改法可以**完全不经过编码器**，改成"原地改流 + 只重加密受影响的
8 字节块 + 改 `0x06`"，把真机上唯一的未知量（编码器输出能否被加载器接受）彻底消掉。

各补丁字节在流里的性质（Part1，流起点 = 文件 `0x200`，解密后）：

```
解压后偏移      性质                                  说明
0x0A0C/0x0A0D   字面量 @stream+0x886 / +0x888          autoskip 用
0x0A0A/0x0A0B   字面量 @stream+0x884 / +0x885          hns-instant 用
0x1352/0x1353   字面量 @stream+0x105D / +0x105F        stage=2 用
0x133E/0x133F   字面量 @stream+0x1052 / +0x1053        （bl 的后半字）
0x133C/0x133D   在匹配内 (disp=3792, len=4) @+0x104F   ✗ 不能原地改
0x089A/0x089B   在匹配内 (disp=118,  len=9) @+0x765    ✗ 不能原地改
```

> 结论：**凡是目标字节落在"匹配"里的补丁（`0x133C`、`0x089A`），都必须整条重压**，
> 也就必须承担编码器风险。D/E 都因此需要重压。

## 3. 各改法的确切内容

### C（推荐：彻底不显示 + 零重压风险）

```
part1 0x1352: 00 21  ->  02 21      ; F 把 stage 直接设成 2（跳过 stage0 淡入 / stage1 等待）
part1 0x0A0C: 23 48  ->  1A E0      ; stage1 的"检测按键/触摸"改成无条件放行（兜底）
新 0x06 = 0x7FF3
```

- `0x1352` 是 F 里 `movs r1,#0` + `str r1,[0x023308E0+0x2C]` 的那条赋值，改成 `#2` 后
  stage 链从 2 开始跑（stage2 负责上屏 DISPCNT/BLDCNT 设置 → 上屏不会黑）。
- 加上 `0x0A0C` 是**兜底**：万一以后有别的路径把 stage 设回 0/1（例如从设置里的
  "开机菜单"重新走一遍），也不会卡在"等确认"。
- 观感：开机 logo → 一段 stage2 的原版淡出过渡 → DS 菜单。**看不到警告页**。
  （你当年测 E 时说的"还是有一个动画"就是这个 stage2 淡出。）

### B（最小改动版）

```
part1 0x1352: 00 21  ->  02 21
新 0x06 = 0xBF2F
```
只 1 字节，效果同 C（但少了兜底）。

### D（= 当年的 v4：最彻底，但需重压）

```
part1 0x133C: 04 F0 A6 F9  ->  C0 46 C0 46   ; bl 0x568C -> nop nop（不装载警告画面数据）
part1 0x1352: 00 21        ->  02 21         ; stage=2（跳过警告阶段）
part1 0x089A: 0F 29        ->  00 29         ; stage2 的 15 帧淡出改瞬时
新 0x06 = 0xDB32      压缩流 51227 字节（槽位 51232，放得下）
```
效果：**警告页不装载、不显示、也没有过渡动画**，直接进菜单，显示正常（上屏不黑）。
代价：含匹配内字节 → 必须整条重压 → 真机需验证编码器输出可被接受。
你当年的评价是"很完美，但太野了，会看着它画出来"。

### E（不装载 + 保留一段淡出）

```
part1 0x133C: 04 F0 A6 F9 -> C0 46 C0 46
part1 0x1352: 00 21       -> 02 21
新 0x06 = 0x248A      压缩流 51225 字节
```
即你当年测的"①还是有一个动画"。比 D 少一刀 `0x089A`。

## 4. 原地（零重压）改法：具体步骤

只适用于**目标字节是字面量**的补丁（B / C / A / `0x0A08` 门槛调整等）。

1. 取 `firmware[0x200 : 0x200+51232]`，用 **KEY1 解密**（参数见下）。
2. 按上面的映射表，把流里对应偏移的**字面量字节**改成新值（只改 1~3 个字节）。
3. **只重新加密受影响的 8 字节块**（KEY1 是 ECB，每 8 字节独立），写回原位；
   其余字节原样不动。
4. 把头部 `0x06`（u16 LE）写成对应常量（B=`0xBF2F`、C=`0x7FF3`、A=`0xCFC3`…），
   或自行计算：`CRC16( 改过的解压后Part1 ‖ 解压后Part2, init 0xFFFF )`。
5. 验证：解密+解压后应看到新字节；5 项校验应全过；文件大小 262144。

KEY1 参数：密钥表 `bios7[0x30 : 0x30+0x1048]`（1042 个 u32）、
`idcode = u32(firmware[0x08])`（本机 `0x6843414D`）、`level=2`、`byte_modulo=0x0C`。
`tools/ndsl_mod.py` 里的 `Key1` 类可以直接用（它解密/加密都实测 byte-exact）。

> 提示：`ndsl_mod.py` 目前只有"改解压后镜像→重压"这一条路径（对 B/C 也安全，
> 因为实测差异字节数就等于补丁字节数）。若要我加一个 `--inplace` 模式（纯原地改流、
> 只重加密受影响块、完全不经编码器），说一声即可。

## 5. 复现命令

```bash
cd /var/home/liu/tmp1/NDSL/NDSL-iQue-256k-Notes/ndsl-hns-mod
FW=../我的固件/FW001656B0043F/firmware.bin
BIO=../我的固件/FW001656B0043F/biosnds7.rom

# C：彻底不显示 + 零重压风险（推荐）
python3 tools/ndsl_mod.py patch "$FW" --bios "$BIO" \
    --spec 'part1:0x1352=0021>0221,part1:0x0A0C=2348>1ae0' -o out/firmware_hns_noshow.bin

# B：最小改动
python3 tools/ndsl_mod.py patch "$FW" --bios "$BIO" \
    --spec 'part1:0x1352=0021>0221' -o out/firmware_hns_noshow_min.bin

# D：当年的 v4（最彻底，需重压）
python3 tools/ndsl_mod.py patch "$FW" --bios "$BIO" \
    --spec 'part1:0x133C=04f0a6f9>c046c046,part1:0x1352=0021>0221,part1:0x089A=0f29>0029' \
    -o out/firmware_hns_v4.bin

# 校验任意成品
python3 tools/ndsl_mod.py verify out/firmware_hns_noshow.bin --bios "$BIO"
```

> ⚠️ **`tools/ndsl_mod.py` 里的 `hns-fade-instant` 预设是错的**：它漏了 `0x133C` 的装载 nop，
> 还多了一条此时无意义的 `0x0A0C`，所以**不等于**当年的 v4。要用真 v4 请照上面第三条显式 spec。
> （该预设待修。）

## 7. 还没做到的：既"一个像素都不出现"又"过渡顺滑"

- B/C 是"警告阶段不跑"，过渡用的是 stage2 的原版淡出 → 已经比较自然；
  但 F 函数体在开机时仍会画 logo 与一个图标（你测 `v2_noload` 时看到的"孤零零的警告图标"
  就来自 F 体内，不在 `bl 0x568C` 那条装载上）。
- 若要连那个图标都不出现，需要继续逆向 **F（Part1 `0x0DD8`）体内 `0x0EA8`–`0x1084` 一带**
  的绘制调用，找到画警告框/图标的那几处，然后**用 B/C 的"字面量原地改"思路**
  （若那些字节也在匹配里，则只能重压）把它们 nop 掉。
- 这条路线未做，属于"彻底到像素级"的后续工作。

## 8. 为什么不走"用户设置位"路线（历史结论）

设置里那几位（bit9 / bit10/11/13/14/15）确实参与"是否显示健康提示"的判断
（`flags.bit8 = !(设置bit10&bit11&bit13&bit14&bit15) | 设置bit9`，映射函数 Part1 `0x5840`），
但**清掉它们等于告诉固件"设置丢了"**，固件会先跑首启向导，向导完成后又把位写回，
警告照旧。所以这条路不通，只能改代码。
