# 256 KiB 中文固件 + 去掉开机健康提示

`scripts/patch_hns_ique.py` 在 `dist/idsl-256k-chs-userp5.bin` 的基础上，钩掉**神游版
P1**（不是日版那份）里的开机健康提示。四种模式，从"页面上不出现"到"连画面数据都不装载"：

| 模式 | 输出文件 | 警告页显示 | 装载警告画面数据 | 过渡 |
|---|---|---|---|---|
| `autoskip` | `…-hns-autoskip.bin` | 显示约 1.5 s 后自动走 | 是 | 原版淡入淡出 |
| `noshow` | `…-hns-noshow.bin` | **不显示** | 是 | stage2 原版淡出 |
| `noload` | `…-hns-noload.bin` | **不显示** | **否** | stage2 原版淡出 |
| `v4` | `…-hns-v4.bin` | **不显示** | **否** | 淡出改瞬时 |

`v4` 就是文档里那版"最彻底"的改法（不装载 + 不跳显示 + 无过渡），也是本文档的重点。

## 1. 为什么要重新定位偏移

`ndsl-hns-mod/` 里的补丁偏移（`0x0A0C`、`0x133C`、`0x1352`、`0x089A`）是**日版/外版
P1** 的。神游 512 KiB 固件的 P1 是另一份构建（解压后 `83332` 字节 vs 日版 `68420`），
代码被整体搬移过，偏移不能照抄。逐条反汇编比对后，钩子落在：

| 作用 | 日版 P1 | 神游 P1 | 原字节 → 新字节 |
|---|---|---|---|
| F 里 `bl 0x568C` 装载警告画面 → nop | `0x133C` | **`0x1394`** | `04 F0 BA F9` → `00 E0 00 E0` |
| F 里 stage 初值 `0` → `2`（跳过警告阶段） | `0x1352` | **`0x13AA`** | `00 21` → `02 21` |
| stage2 的 15 帧淡出改瞬时 | `0x089A` | **`0x08D6`** | `0F 29` → `00 29` |
| stage1 里"等按键/触摸"改无条件放行（兜底） | `0x0A0C` | **`0x0A48`** | `23 48` → `1A E0` |

依据（都可复现）：

- 这些指令在神游 P1 里与日版**逐字节相同**，只是整体位移不同：早期区域 `+0x3C`
  （`0x089A→0x08D6`、`0x09F0→0x0A2C`、`0x0A0C→0x0A48`），F 区域 `+0x58`
  （`0x133C→0x1394`、`0x1352→0x13AA`）。
- F 里 `str r1,[r0,#0x2C]` 写的 stage 变量：日版 `0x023308E0+0x2C`，神游
  `0x02334320+0x2C`；两边各处 stage 写入序列都是 `5,10,10,9,7,8,6,5,4,3,2,1,1,0`，
  顺序与数值完全一致 —— "初值设成 2"在两份固件里含义相同，指向同一个 stage 2。
- `0x1394` 与日版 `0x133C` 一样紧跟 `movs r1,#1`、后面接着同一段 flags 操作，
  是 F 里装载警告画面资源的那一次调用。

### 为什么 nop 用的是 `00 E0 00 E0` 而不是 `C0 46 C0 46`

两者都是 Thumb 的等价空操作（`b +0` / `mov r8,r8`）。但 `v4` 需要**整条重压 P1**，
用 `C0 46 C0 46` 压出来是 `62673` 字节，比 P1 槽位（`0x280..0xF750` = `62672`）
**多 1 字节**；换成 `00 E0 00 E0` 正好 `62672`，于是**不必搬动 P2/P3/P4/P5**，
保持已实机验证过的分量布局不变。

## 2. 风险说明（重要）

本项目在真机上唯一翻过车的是**重新压缩的编码器输出**（`dsfwtool -comp` 压 P5 白屏，
见根 README）。本脚本把这条风险压到最低，但两种模式的量级不同：

- `noshow` / `autoskip`：只改字面量。先用 `lz77_compress()` 复刻原流（**逐字节相同**
  才继续），改完再压，流内只有 2~3 个字节变化，写回时**只重新加密受影响的 1~2 个
  8 字节块**。相对未打补丁镜像只差 10~18 字节 —— 等价于"原地改流"，零编码器风险。
- `noload` / `v4`：`0x1394`、`0x08D6` 两处落在 LZ77 的**匹配内部**，必须整条重压
  （`C0 46…` 那种原地改流不可行）。脚本为此额外做了两层验证：
  1. 编码器对被改前的神游 P1 **逐字节复刻**（不满足就直接拒绝出图）；
  2. 对原流与新流都跑一遍**加载器不变量检查** —— 重叠匹配（`长度 > 位移`）必须是
     偶位移。神游 P1 原有 107 处重叠匹配，全部偶位移；v4 重压后同样是 107 处、
     全部偶位移（这条规则就是"软件解码器全过、真机不启动"的那类坑）。

**结论（2026-10-13 真机实测后）**：`v4` 与 `autoskip` 两块镜像都已刷进真机，**正常开机、
正常使用** —— 也就是说 `v4` 那条"整条重压 P1"的流，真机加载器是接受的，
上面"未经真机验证"的保留意见可以撤销。`noshow` / `noload` 这两份当时没有单独刷，
但它们各自只是已验证镜像的钩子增删（`noshow` = `autoskip` + stage 钩子，
`noload` = `v4` 去掉淡化钩子），且每一处钩子都分别在已验证镜像里出现过。

## 3. 已知残留（项目原文档第 7 节）

按 `ndsl-hns-mod/彻底去掉健康提示-直接进菜单.md` 第 7 节的记录：F 函数体本身（不只是
`bl 0x568C` 那次装载）在开机时还会画 logo 与一个小图标。`v4` 已经把**装载**和**警告
阶段**都去掉，但如果真机上仍看到那个独立图标，它就在 F 体内 `0xEE4–0x10C0` 一带的绘制
调用里，需要继续逆向定位后单独 nop 掉（属于"像素级"后续工作，未做）。本次 `v4` 真机
实测正常使用，但该残留图标是否仍可见没有专门确认；如果还能看到它，就按这条继续处理。

## 4. 复现

```bash
cd NDSL-iQue-256k-Notes

# 1) 未打补丁的 256 KiB 中文固件
DSFWTOOL=/path/to/dsfwtool \
IQ_FW="材料/网友分享的神游DSL固件/idsl-fw.bin" \
TARGET_FW="材料/我的固件 FW001656B0043F/firmware.bin" \
./scripts/build_firmware_userp5.sh

# 2) 打补丁（bios7 默认取 材料/我的固件 FW001656B0043F/biosnds7.rom）
for m in noshow noload v4 autoskip; do
  python3 scripts/patch_hns_ique.py dist/idsl-256k-chs-userp5.bin \
          -o dist/idsl-256k-chs-userp5-hns-$m.bin --mode $m
done
```

脚本自带校验：编码器复刻断言、往返、流长度/槽位、LZ77 重叠匹配不变量、全部 5 项
CRC、改动字节数，任一项不符即非零退出。

## 6. 真机验证结果（对照主 README 的踩坑记录）

**2026-10-13 实测**：下列两块镜像已刷入真机，都能**正常开机并正常使用**。

| 镜像 | 真机 | 备注 |
|---|---|---|
| `hns-v4` | ✅ 实测可用 | 不装载 + 不显示 + 无过渡；整条重压 P1 |
| `hns-autoskip` | ✅ 实测可用 | 照原版显示约 1.5 s 后自动进菜单 |
| `hns-noshow` | 未单独刷 | = `autoskip` + stage 钩子，零重压风险 |
| `hns-noload` | 未单独刷 | = `v4` 去掉淡化钩子 |

**基准镜像**：`dist/idsl-256k-chs-userp5.bin` 与主 README 里那份"已在真实日版
DS Lite 上刷写验证通过"的镜像 **sha256 逐字节相同**，构建链路里没有引入新东西。

**对照主 README 文首 / 第 7 条**：那条白屏记录讲的是 **P3/P4/P5 的 vpk 编码器**
（`dsfwtool -comp` 压 P5 → 真机纯白屏）。本构建没有碰这条路径：P5 用的是
`ndsl_mod.vpk_compress()`（就是实机验证过的那条），P3/P4 是用 `dsfwtool -comp`
压**未改动的原始数据**（文档说明这条是逐字节相同的）。所以白屏那类坑与本基准无关。

**对照主 README 第 8 条**："给 iQue 的 P1 打 `0x0A48: 2348 → 1ae0` → 现象无变化"这条
要注意上下文：那是在**已经白屏**的镜像上做的实验，屏幕上什么都没显示，"无变化"只能
说明白屏不是警告画面那条路引起的，**既不能证明也不能否定补丁的效果**；而且那次只打了
`autoskip` 一个钩子。本次实测才真正验证了补丁行为。

**分模式的改动量**（关键区别是"要不要重压 P1"）：

| 模式 | 相对实机验证版的差异 | 编码器风险 |
|---|---|---|
| `noshow` | P1 解压后差 **3 字节**，压缩流也正好差 **3 字节**（全是字面量）；整镜像 18 字节 | **零** —— 等价于"原地改流"，与基准同级 |
| `autoskip` | 同上，2 字节 / 整镜像 10 字节 | 零 |
| `noload` | 解压后差 5 字节，但**压缩流差 56584 字节**（整条重压） | 与 `v4` 同一条已验证路径 |
| `v4` | 解压后差 6 字节，但**压缩流差 57734 字节**（整条重压） | ✅ 真机已接受 |

`noload`/`v4` 重压前，编码器对被改前的 P1 逐字节复刻、重压后重叠匹配全部偶位移，
这两条能证的东西都证了；真机实测则补上了软件侧证明不了的那一环。

**建议**：要稳妥就先刷 `noshow`（页面同样完全不出现，且与实机验证版只差 3 个流字节）；
确认机器和中文界面都正常后，再决定要不要为"不装载 + 无过渡"去承担重压风险刷 `v4`。
